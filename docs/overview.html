Meridian Freight, Breakdown-to-Resolution System

When a truck breaks down, this decides what happens next in seconds, not forty minutes.

A dispatcher used to check five systems by hand to reroute a broken-down truck. This replaces that scramble with one automated pipeline: every ticket is validated, matched against the fleet, checked against fourteen dispatcher rules, and resolved, with a human approving only the step that actually leaves the building.

How a ticket moves

Seven steps, always in the same order

Every breakdown ticket, whether it arrives in the main queue or drops in later as a surprise file, passes through the same seven checkpoints. Nothing skips a step, and nothing repeats one.

1

Validate

Is this ticket a duplicate of one already seen, is it complete enough to act on? A record with a missing vehicle, hub, or issue field is quarantined with a clear reason and an alert. It is never dropped silently and never allowed to crash the run.

2

Enrich

The ticket is joined against the fleet, driver roster, client contract, and maintenance history, so every later decision has full context instead of just the four fields the ticket itself contains.

3

Classify

Severity and the required action are decided by consulting the fourteen encoded dispatcher rules, not a guess. Every classification cites the specific rule that produced it.

4

Select a replacement vehicle

Every active truck is checked against the same rules: available, permitted for the season on this route, not overdue on maintenance, not already claimed by another ticket this run. If nothing clears every rule, the ticket stops here and waits for a person.

5

Record one work order

Written exactly once per ticket, no matter how many times that ticket ID appears in the queue.

6

Draft the client notification

The message is written and queued behind a human approval gate, with the full reasoning and rule citations shown to the approver before it goes anywhere.

7

Write the audit record

What was decided, using what data, under which rule, by whom or by what, recorded for every single step of every single ticket.

Real-world messiness

The four ways this actually gets tested

A clean demo is not the bar. These are the specific failure modes the system is built to survive, each one verified by actually running it, not just reasoning about the code.

↻Duplicate tickets

A sync fault means the same ticket ID can appear more than once. Each one is processed exactly once. Running the whole pipeline twice back to back produces identical output, nothing doubled.

⚠Broken records

Missing vehicle, missing hub, unreadable fields. The ticket is quarantined with a clear reason and an alert. It never crashes the run and never gets silently dropped.

↯The surprise file

A background watcher checks the inbox folder every eight seconds. A file in a completely different shape lands, has its fields matched automatically, and flows through the same seven steps. No restart, no manual step. Verified live.

🔒No eligible truck

When nothing passes every rule, the system does not force a bad match. It stops, shows a dispatcher every candidate and why each one failed, and waits for a judgment call.

Expert knowledge, encoded

Fourteen rules from a 14-year dispatcher's interview

The rules are not buried in code. They are a readable table, and each one is traceable to the exact line of the interview transcript it came from. One of them is the clearest proof the system respects real expertise over the obvious answer:

RULE R-09, SOURCING OVERRIDE

The obvious move when a truck breaks down is to send a replacement from the nearest hub. But if the breakdown happens within 50km of its own origin hub, the rule says send the replacement from there instead, even when a closer hub exists.

The system checks this every time, cites the rule by ID in the work order, and a dispatcher who overrides it manually has to type a reason that becomes a permanent, clearly labeled part of the record, never mistaken for a rule-compliant pick.

The one non-negotiable

Personal data never leaves the building raw

✓

Phone numbers, ID numbers, license numbers: masked before they are ever stored

Not removed before sending, removed before saving. Every driver record keeps only a one-way hash. Every free-text note is redacted at the moment it is ingested. A second, independent scanner then re-checks every single file the system ever produces (work orders, client messages, the dashboard, CSV exports) before a run counts as complete. Nothing raw can leak because nothing raw is ever kept.
